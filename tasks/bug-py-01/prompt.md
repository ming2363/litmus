# 修复发布目录的版本号排序

内部组件库「harbor」用版本号给构建产物排序，并判断某个构建是否满足依赖约束。现在预发布版本和正式版本的先后关系是错的，例如 `1.10.0-rc.1` 被排到了 `1.10.0` 后面。请修正比较逻辑，使下面的规则全部成立。

## 版本号语法

只接受下面这种写法，否则 `parse_version` 抛出 `ValueError`，异常消息里必须包含原始输入字符串：

- 主体是 `主版本.次版本.修订号`，三段都是十进制非负整数，不允许前导零（`0` 本身可以）。
- 可选的预发布标记：`-` 后面跟一段或多段用 `.` 分开的标识。每一段只含字母、数字和连字符，不能为空。纯数字的段同样不允许前导零。
- 可选的构建标记：`+` 后面跟一段或多段用 `.` 分开的标识，字符集与预发布相同，构建标记允许数字段有前导零。
- 构建标记可以出现在没有预发布标记的版本上，也可以出现在预发布标记之后。不接受其他字符、空串、缺少某一段、多余的 `+` 或 `-`。

## 先后关系

`compare(left, right)` 接收两个版本字符串，按优先级返回 `-1`、`0` 或 `1`。构建标记不参与比较。规则与语义化版本的优先级一致：

1. 先按主版本、次版本、修订号的数值比较。因此 `1.9.0` 早于 `1.10.0`，也早于 `1.10.0-rc.1`。
2. 主体相同且都没有预发布标记时，优先级相同。
3. 主体相同但只有一边有预发布标记时，**有预发布标记的版本更早**。因此 `1.10.0-rc.1` 早于 `1.10.0`，`1.0.0-alpha` 早于 `1.0.0+build.5`。
4. 两边都有预发布标记时，从左到右比较标识：纯数字标识按数值比较，所以 `beta.2` 早于 `beta.11`；数字标识早于非数字标识，所以 `alpha.1` 早于 `alpha.beta`；非数字标识按 ASCII 字典序比较。若前面的标识都相同，标识段更少的版本更早，所以 `alpha` 早于 `alpha.1`。

`sort_versions` 按上述优先级从早到晚排序，返回新列表，不修改入参。

## 约束与目录

`parse_constraint` 只接受一个比较符加一个版本，比较符为 `>=`、`>`、`<=`、`<`、`==`、`!=`，比较符和版本之间可以有空白。`Constraint.matches(version)` 用上面的优先级判断。

`Catalog.add(name, version)` 记录一个组件的构建。`Catalog.latest(name)` 返回该组件优先级最高的版本字符串；没有记录时抛出 `KeyError`。`Catalog.satisfying(name, constraint)` 返回满足约束的版本字符串列表，从早到晚排序。

`Dependency(name, constraint)` 表示一条依赖。`resolve(catalog, dependencies)` 为每条依赖选择满足约束的最新版本，返回 `{组件名: 版本}`。没有候选时抛出 `KeyError`，消息里包含组件名。

可以修改 `harbor/` 下的 Python 文件，不要改测试。比较结果不能依赖当前时间或随机数。
