# litmus 设计文档

> 状态：已确认方案，已完成一轮自查修订，待拆实现计划
> 日期：2026-11-08

## 1. 目标

在任意 Agent 工具里（Codex、OpenCode、Claude Code 等），选中想测的模型，粘贴一段固定提示词。模型自己一题一题做完，最后输出一份**客观指标**报告。

- 只测用户指定的那个模型，报告里不和其他模型比较，也不给"换 / 不换"的结论。报告给出一个综合分（见 6.1），用户拿不同模型的报告自己比较。
- 测的是"工具当前配置下的模型"：工具里选了哪个模型就测哪个，litmus 不改工具配置。
- 全部在本机运行，没有服务端。只支持 macOS / Linux。

## 2. 使用方式

### 2.1 一个目录装下全部

题目、答案、提示词、判分脚本全部放在 litmus 这一个目录里。测试时只需要把这个目录交给被测模型，目录外不依赖任何文件。

```
litmus/
├── PROMPT.md       # 提示词：每次测评复制这个文件的内容给被测模型
├── litmus.py       # 做题入口：start / next / check / submit / report
├── author.py       # 出题入口：seal / unseal / selftest / lint（被测模型用不到）
├── litmus/         # 判分、加解密、报告等实现代码
├── tasks/          # 题目：题面 + 起始代码，被测模型只看这里
├── answers/        # 答案：隐藏测试、标准答案、参考解，全部加密
├── runs/           # 测评过程数据（git 忽略）
├── reports/        # 测评报告（git 忽略）
└── docs/
```

### 2.2 测评步骤

1. 用 Agent 工具在 litmus 根目录打开**新会话**，选好模型。
2. 把工具设成**自动批准命令**，否则每条命令都会停下来等你点同意，没法一口气跑完：
   - Codex：`--full-auto` 或把审批策略设成 never
   - Claude Code：auto 或 bypass 权限模式
   - OpenCode：把权限设成 allow
3. 把根目录 `PROMPT.md` 的内容整段复制给模型。
4. 等它跑完，终端会给出综合分摘要和报告文件路径。用浏览器打开 `reports/` 下的 HTML 报告查看全部内容，**以文件为准**。

- 快速模式：`PROMPT.md` 里同时提供标准版和快速版两段提示词，复制快速版即可。
- 中途断了：原会话里说"继续"；会话没了就开新会话，重新复制提示词，`start` 会接着上次的进度做。

### 2.3 `PROMPT.md` 的内容

```
你正在参加 litmus 编程能力测评。规则：
1. 在本目录执行 python3 litmus.py start，然后严格按命令输出的指示一题一题做，
   中途不要停下来问我，直到出现 ALL DONE。
2. 只看 tasks/ 下当前题目和 runs/ 下分配给你的工作目录。
   不要打开 answers/ 目录，不要运行 author.py，不要修改 litmus.py 和 litmus/。
3. 每题独立完成，不要上网搜答案，不要把任务交给其他模型或工具代做。
4. 最后执行 python3 litmus.py report，把输出原样给我。
```

**第 2 条只是第一道防线，不靠它保证公平。** 即使模型无视这条规则去读 `answers/`，读到的也只是密文；直接改判分代码，成绩会被判为无效（见 4.1）。

## 3. 运行流程

```
start ──► next ──► 模型在工作目录做题（可用 check 自测）──► submit ──► next ──► … ──► ALL DONE ──► report
```

### 3.1 做题命令（`litmus.py`）

| 命令 | 作用 |
|---|---|
| `start [--quick] [--new]` | 环境检查和干净度检查（见 4.2），新建或续跑一次测评（run），输出做题规则和本次测评的**运行标记**（见 6.4）。已有未完成的测评时默认续跑；`--new` 强制新开，旧的标为"已放弃" |
| `next` | 发下一题：把起始代码复制到独立工作目录，输出题号、维度、工作目录的绝对路径、题面、答案格式。当前题还没提交时重复输出当前题，不跳题；全部做完时输出 `ALL DONE` |
| `check` | 在当前题的工作目录里自测：代码题跑可见测试，答案题只校验答案文件格式（不判对错） |
| `submit` | 提交当前题：脚本当场判分，只回复"已提交"和下一步该做什么，**不透露对错**。每题只能提交一次 |
| `skip` | 放弃当前题，按不通过计分 |
| `status` | 查看进度 |
| `report` | 汇总成绩，写入 `reports/<run-id>.html`、`.md`、`.json`；终端只输出综合分摘要和文件路径，不输出表格 |

**每条命令的输出都以明确的下一步结尾**，比如"下一步：执行 python3 litmus.py next"。长会话发生上下文压缩后，模型可能忘了最初的提示词，靠每次命令输出里的这句话也能一直往下走。

### 3.2 出题命令（`author.py`，单独入口）

| 命令 | 作用 |
|---|---|
| `seal <题号\|--all>` | 把 `answers/<题号>/` 下的明文加密成 `answers/<题号>.grade.enc` 和 `answers/<题号>.solution.enc`，然后**删除明文目录** |
| `unseal <题号>` | 解密回 `answers/<题号>/`，用于修改题目 |
| `selftest [题号]` | 逐题自检，规则见 7.3 |
| `lint` | 仓库结构检查：禁止出现的文件、manifest 和题目目录是否一致、题号是否重复 |

出题命令放在单独的入口里，做题流程的输出和帮助信息都不提到它。另外，只要本机有未完成的测评，`unseal` / `selftest` 就拒绝运行。所有解密操作都写一条审计记录到 `runs/audit.log`，`report` 发现测评期间有判分以外的解密，就把成绩标为**无效**。

### 3.3 状态管理

- 状态文件 `runs/<run-id>/state.json`，用"写临时文件再重命名"的方式原子写入。
- 所有命令执行前先拿文件锁（`fcntl.flock`）。Agent 工具可能并行调用两条命令，比如同时 `submit` 和 `next`，加锁防止状态错乱。
- 判分发生在 `submit` 那一刻，结果直接存进状态。之后模型再改工作目录也不影响成绩。

## 4. 防作弊与测量可信度

### 4.1 风险与处理

| 风险 | 结构上的处理 |
|---|---|
| 模型自己判自己 | 判分完全由脚本执行，不经过模型 |
| 模型偷看答案 | 两道防线：`PROMPT.md` 明确禁止打开 `answers/`；就算模型无视规则，`answers/` 里也全是密文。每题加密成两份：`grade.enc` 是判分用的隐藏测试和标准答案，`solution.enc` 是参考解，只有 `selftest` 用。`submit` 只解密**当前这一题**的 `grade.enc`，判完立即删除；它解密时模型已经交卷，看到也没用。后面题目的答案始终是密文 |
| 出题时留下的明文答案 | `seal` 加密后删除明文目录。`start` 检查到 `answers/` 下有明文目录就拒绝开始，提示先 `seal` |
| 公开仓库被爬进训练数据 | 题面明文公开没关系，只看题面学不到答案；能让模型背出答案的测试和参考解都是密文 |
| 反复试错刷分 | 每题只能提交一次，提交后不反馈对错 |
| 模型运行出题命令解密 | 见 3.2：有未完成测评时出题命令拒绝运行，所有解密都有审计记录，异常解密会让成绩作废 |
| 篡改判分脚本或测试 | `start` 记录 HEAD 提交号；`submit` / `report` 校验已跟踪文件和 HEAD 一致，且 HEAD 没变，不一致则成绩标为**无效** |
| 在工作目录里伪造测试运行器 | 判分时用的测试运行器来自 `litmus/` 本身，不用工作目录里的任何运行器 |
| 工具自动加载仓库里的 AGENTS.md / CLAUDE.md / GEMINI.md，干扰做题 | 仓库任何位置都**禁止**出现这类文件，`lint` 和 `start` 都会检查 |
| 被测工具把任务外派给别的模型 | `start` 读取 `~/.claude/ai-relay/mode`，不是 `off` 就拒绝开始，并提示关闭命令。关闭 ai-relay 时也会一并禁用 Codex 插件 |
| 只做一部分题就结束 | 未提交的题在 `report` 时一律按不通过计分，报告里列出未完成数 |
| Code Review 题靠每行都提意见刷命中 | 见 5.3：每题最多提 10 条，而且命中要求类别也对 |

**剩余风险**：模型刻意读 litmus 源码里的内置密钥，自己写代码解密 `answers/`；或者去翻本机 AI 工具的会话记录（出题时的对话里有明文答案）。这些都要主动绕过规则、额外写代码才做得到，属于刻意作弊，个人工具不防到这个程度。

### 4.2 `start` 的检查清单

任何一项不满足，就拒绝开始并给出修复方法：

1. Python ≥ 3.9；`javac` 和 `java` 都存在，版本 ≥ 17（只有 JRE 没有 `javac` 也算不满足）；`git` 存在
2. 当前目录是 git 仓库；`litmus.py`、`litmus/`、`tasks/`、`answers/` 下没有未提交的改动
3. `answers/` 下没有明文目录（全部已 `seal`）
4. 不存在 AGENTS.md / CLAUDE.md / GEMINI.md
5. 用内置密钥解开一题做验证，确认加解密正常
6. ai-relay 模式为 `off`，或者本机没装 ai-relay
7. 清理上次判分崩溃时可能残留的判分临时目录

## 5. 评测维度、题量与判分

### 5.1 题量

全部题目都是手写的小型独立项目，Java 和 Python 大约各占一半。每题几百到一两千行代码，编译和跑测试都在秒级。

| 维度 | 标准题数 | 快速模式 | 参考榜单 | 结果形式 |
|---|---|---|---|---|
| 修 Bug | 12 | 3 | SWE-bench | 改代码 |
| 新功能 / 跨文件改动 | 8 | 3 | FeatureBench | 改代码 |
| 终端实操 | 8 | 3 | Terminal-Bench | 改工作目录里的文件状态 |
| 工具调用 | 8 | 3 | BFCL / τ-bench | `answer.json` |
| 读代码 | 8 | 3 | RULER / MRCR | `answer.json` |
| 小范围编辑 | 8 | 3 | Aider | 改代码 |
| Code Review | 8 | 3 | — | `review.json` |
| **合计** | **60** | **21** | | |

- 每题标难度（易 / 中 / 难），每个维度按大约 1 : 2 : 1 分配。报告按难度分别给出通过率。
- 快速模式抽哪 21 题，固定写在 `manifest.json` 里，每个维度易、中、难各一题。
- **题目顺序固定**，所有模型按同一顺序做。后面的题会受前面上下文的影响，但对每个模型的影响相同。报告逐题记录序号和耗时。

### 5.2 代码类判分（修 Bug、新功能、小范围编辑）

判分在 `runs/<run-id>/.grade/<题号>/` 里进行，按顺序执行：

1. **复制**模型的工作目录。
2. **可合入性检查**：拿工作目录和起始代码逐文件比较，下面任一项不满足就判不通过，并记为"可合入性否决"：
   - 新增、修改、删除的文件都在 `allowed_paths`（glob 规则）范围内。以下构建产物和工具文件不算改动，直接忽略：`*.class`、`out/`、`build/`、`target/`、`__pycache__/`、`*.pyc`、`.pytest_cache/`、`.git/`、`.DS_Store`
   - 可见测试文件没有被修改或删除
   - 代码能编译（Java 用 `javac`，Python 用 `py_compile`）
   - 只针对小范围编辑：改动行数（统一换行符、去掉行尾空白后用 difflib 统计）不超过 `max_changed_lines`
3. **覆盖隐藏测试**：解密 `grade.enc`，把隐藏测试铺到判分目录。同路径的文件以隐藏版本为准，这样模型改了测试也没用。
4. **运行测试**：用 `litmus/` 自带的运行器，结果按测试用例逐条输出成 JSON。单个用例可以单独设超时（性能题用，见 7.3 第 10 条），整体也有超时（默认 120 秒），超时都算不通过。
5. **判定**：`grade.enc` 的元数据里列着 F2P（起始代码失败、应该修好的用例）和 P2P（起始代码就通过、不能被改坏的用例），两份全部通过才算这题通过。长任务没全过时可以按 F2P 通过比例拿部分分，规则见 6.1。
6. **清理**：用 `try/finally` 保证无论结果如何，都删除判分目录和解密出来的内容。

测试运行器：

| 语言 | 运行器 |
|---|---|
| Java | litmus 自带一个单文件运行器：通过反射执行测试类中 `public void test*()` 方法，失败即抛异常，结果逐条输出 JSON。编译时运行器放在 classpath 最前面 |
| Python | litmus 自带一个运行器模块，在子进程里以编程方式调用 `unittest`，结果逐条输出 JSON，不解析 unittest 的文本输出 |

### 5.3 终端实操、答案类判分

| 维度 | 判分规则 |
|---|---|
| 终端实操 | 所有状态都在工作目录内：不联网、不用 sudo、不做全局安装、不需要常驻进程。判分时运行 `grade.enc` 里的检查脚本，检查最终的文件和内容，只判过或不过 |
| 工具调用 | 题面给出工具定义（JSON Schema）和场景，`answer.json` 写调用列表；不该调用任何工具时写空列表。判分规则：函数名完全一致；必填参数按题目给定的归一化规则比较（去首尾空白、日期格式统一等）；不能出现定义里没有的参数；`ordered: true` 的题按顺序比较，否则当作集合比较。JSON 不合法直接判不通过 |
| 读代码 | 题面规定答案格式：路径用相对路径，方法写成 `类名#方法名`，调用链按顺序写成列表。归一化后和标准答案完全一致才算通过 |
| Code Review | 题面给出 diff，同时提供改动后的完整文件。**行号一律以改动后的文件为准**。`review.json` 每条包含：文件、行号、类别（从题面给定的固定列表里选，如空指针、越界、资源泄漏、并发、注入、逻辑错误）、描述。命中条件是文件相同、行号相差不超过 3 行、类别一致。一条意见最多命中一个预埋问题，按行号距离一一配对。每题最多 10 条，超过直接判不通过。**命中全部预埋问题**才算这题通过 |

## 6. 报告

### 6.1 综合分

报告最上面给一个 0～100 的综合分，用来比较不同模型的强弱。只有题库版本和模式（标准 / 快速）都相同的两份报告，综合分才能直接比较。报告里写明题库版本（`manifest.json` 与全部 `task.json` 的摘要）。

**综合分 = 正确性分 × 效率系数**

**正确性分（0～100）**：按难度加权的得分率。每题权重：易 1、中 2、难 3、长任务 6。

```
正确性分 = 100 × Σ(每题权重 × 该题得分比例) / Σ(全部题的权重)
```

**单题得分比例（0～1）**：

- 通过的题得 1。
- 易、中、难题不通过得 0，只判全对或全错。
- 长任务（`tests` 判分）不通过时，得分比例 = 通过的 F2P 用例数 ÷ F2P 用例总数。但下面任一情况得 0：可合入性否决；没跑出测试结果（编译失败、整体超时）；任何一条 P2P 用例失败（改坏原有功能的代码不能合入，做对多少新功能都不算）。

未完成、跳过都得 0。难题权重高，是因为易题几乎所有模型都能做对，区分度主要来自中、难题和长任务。长任务给部分分，是因为它的隐藏测试有几十条、边界情况多，强模型也常差一两条；只判全对全错的话，"差一条"和"完全没做"都是 0，权重最高的题反而拉不开差距。易、中、难题的用例少，每条都是题目要考的核心点，仍然只判全对全错。

**效率系数（0.75～1.00）**：

```
效率系数 = 0.75 + 0.15 × 时间分 + 0.10 × token 分
```

正确性决定了综合分的至少 75%，效率最多影响 25%。一个模型全部做对但又慢又费 token，效率系数最低也有 0.89（见下面的下限），只比又快又省的模型低 11%。

**时间分（0～1）**：只按**得分比例大于 0 的题**计算，得 0 的题不计入。得 0 的题已经在正确性分里扣过了；如果把它们也算进时间分，"又快又错"反而会拿到时间分。加权平均时每题的权重是"题目权重 × 得分比例"，拿部分分的长任务做对得越少，它的快慢对时间分的影响越小。

对每道得分比例大于 0 的题，用"实际耗时 ÷ 参考时长"得到比值 r（参考时长是 `task.json` 的 `ref_minutes`）：

- r ≤ 1：该题时间得 1
- r > 1：该题时间得 `max(0.6, 1 − 0.2 × log2(r))`。慢一倍得 0.8，慢三倍及以上得 0.6，不再往下扣

再按上面的"题目权重 × 得分比例"加权平均。设下限 0.6，是因为耗时会受 API 限流、网络和中途暂停影响，并且慢但做对的结果仍然有用。所以时间对综合分的影响最多是 0.15 × 0.4 = 6%。不设超时判负。

**token 分（0～1）**：同样只按得分比例大于 0 的题计算，权重同样是"题目权重 × 得分比例"。每题的计费等价 token：

```
计费等价 token = 未命中缓存的输入 + 缓存写入 + 输出（含思考） + 0.1 × 缓存读取
```

缓存读取按 0.1 计，因为各家缓存命中的价格大约是正常输入的十分之一；不打折的话，缓存用得多的工具会被不公平地算成"费 token"。各解析器要先把字段统一成这个口径（例如 Codex 的 `input_tokens` 含缓存命中，要先减掉；OpenAI 系的输出已含思考）。

每题按难度有一个参考预算：易 4 万、中 10 万、难 25 万、长任务 80 万。用量不超过预算得 1，超过时得 `max(0.5, 1 − 0.25 × log2(用量 ÷ 预算))`，再加权平均。

token 未采集到时（工具不在支持列表，或解析失败），token 分记为"未采集"，效率系数改为 `0.75 + 0.25 × 时间分`，报告注明。

**所有题得分比例都是 0 时**，正确性分为 0，综合分为 0，时间分和 token 分记为"无"。

### 6.2 其他指标

综合分下面照常列出客观明细：

| 指标 | 来源 |
|---|---|
| 正确性分、时间分、token 分、效率系数 | 按 6.1 计算 |
| 通过题数 / 总题数，附 95% 置信区间（Wilson 区间） | 脚本判分 |
| 各维度、各难度通过率，附 95% 置信区间 | 脚本判分 |
| 可合入性否决数、未完成数、跳过数 | 脚本记录 |
| Code Review 的额外条目数（预埋问题之外的意见，只计数不判对错） | 脚本统计 |
| 每题得分比例（长任务可能是部分分） | 脚本判分 |
| 每题耗时（从 `next` 到开始判分，不含判分时间）、参考时长、比值 r、该题时间得分 | 脚本记录 |
| 中断记录：测评期间重新执行过几次 `start`、各在哪道题 | 脚本记录 |
| token 用量（输入 / 输出 / 缓存 / 思考）、每题计费等价 token 和该题 token 得分、模型 ID | 读工具的会话日志，见 6.4 |
| 工具名称、litmus 提交号、题库版本、模式、JDK / Python 版本、开始和结束时间 | `start` 时检测 |
| 成绩是否有效，无效的原因 | 防篡改校验和审计记录 |

成绩无效时，综合分照常计算，但在分数旁标"无效"和原因。

### 6.3 文件

- `reports/<run-id>.html`：给人看的主报告。单文件、样式和脚本全部内联、不引用任何外部资源，断网也能打开；逐题表可按状态和维度筛选、点表头排序，失败原因默认收起
- `reports/<run-id>.md`：同样内容的 Markdown 版，方便贴进文档或聊天
- `reports/<run-id>.json`：机器可读的完整数据，为以后合并多次测评、计算 pass^k 留好接口
- run-id 的格式是 `<日期时间>-<工具>-<模型>`，其中所有不能用作文件名的字符（如 `/`、`:`、空格）都替换成 `-`。模型未知时写 `unknown`。

### 6.4 token 与模型 ID 的采集

- **按运行标记定位会话**：`start` 输出一个随机的运行标记（如 `LITMUS-RUN-7f3a9c`），每次 `next` 输出题目标记（如 `LITMUS-TASK-bug-java-03`）。这些输出会被工具记进自己的会话日志，解析器只认包含本次运行标记的会话文件。这样即使你同时在这个目录开着别的会话，或者中途换了新会话续跑，也能准确找到对应的日志。
- **逐题切分**：按日志里题目标记出现的顺序切分 token 用量，不依赖时间戳。
- **子代理**：Claude Code 的子代理日志在单独的文件里，按同一个运行标记一起统计。
- **模型 ID**：列出日志里出现过的所有模型 ID 及各自的用量。中途换过模型，报告里能直接看出来。

| 工具 | 日志位置 | 解析方式 |
|---|---|---|
| Codex | `~/.codex/sessions/**/rollout-*.jsonl` | JSONL |
| Claude Code | `~/.claude/projects/<编码后的路径>/` 下的 `*.jsonl`，含子代理文件 | JSONL |
| OpenCode | `~/.local/share/opencode/opencode.db` | 标准库 `sqlite3`，只读打开 |

解析失败或工具不在表里的，标"未采集"，其余指标照常出。解析器要能容忍日志格式变化：遇到不认识的行就跳过，不能让整份报告失败。

## 7. 题目规范

### 7.1 目录结构

题目和答案分放在两个目录，被测模型只需要看 `tasks/`：

```
tasks/
├── manifest.json               # 题目固定顺序、快速模式抽选的题
└── <题号>/
    ├── task.json               # 元数据，见 7.2
    ├── prompt.md               # 题面
    └── repo/                   # 起始代码（含可见测试）

answers/
├── <题号>.grade.enc            # 加密：隐藏测试 / 检查脚本 / 标准答案 + F2P、P2P 列表
├── <题号>.solution.enc         # 加密：参考解，只给 selftest 用
└── <题号>/                     # 明文，只在出题时存在，被 git 忽略，seal 后删除
    ├── grade/
    └── solution/
```

题号格式：`<维度缩写>-<语言>-<序号>`，如 `bug-java-03`、`tool-py-02`。

### 7.2 `task.json` 字段

`id`、`dimension`、`lang`（`java` / `python` / `none`）、`difficulty`（`easy` / `medium` / `hard` / `long`，`long` 是长任务）、`title`、`ref_minutes`（参考时长）、`grader`（`tests` / `terminal` / `tool_call` / `read_code` / `review`）、`allowed_paths`（代码类）、`max_changed_lines`（小范围编辑）、`answer_file`（答案类）。

### 7.3 出题质量要求（`selftest` 能自动检查的都会自动检查）

1. **起始状态必须不通过**：代码题的 F2P 用例在起始代码上全部失败、P2P 用例全部通过；终端题的检查脚本在起始状态下判不通过；答案题的空答案判不通过。
2. **参考解必须通过**：代码题和终端题套上参考解后判通过；答案题的标准答案判通过。
3. **结果稳定**：上面两项各跑 3 次，结果必须一致，排除依赖随机数、时间或执行顺序的不稳定测试。
4. **测试不能超出题面**：隐藏测试只能检查题面写明的行为。测试会用到的类名、方法签名、异常类型、输出格式，题面里都要写清楚。SWE-bench Verified 就是因为测试要求超出题面而被弃用的。
5. **独立审题**：每题入库前，交给**另一个模型**只看题面和起始代码来做。做错的题人工检查：是题目没写清楚，就改题；是模型能力问题，就保留。
6. **兼容范围**：Python 代码兼容 3.9 到 3.14，Java 代码只用 17 的特性。全部文件使用 UTF-8 编码和 LF 换行。
7. **难度校准**：第一批题出完后，用一强一弱两个模型跑一遍快速模式。所有模型都能做对的题和所有模型都做不出来的题区分不出水平，需要替换或调整难度。
8. **公开流行题只借形式，不照搬**：社区里流传的测试题（见 7.4）早已进入训练数据，有的还被厂商专门优化过。只借用它们考察能力的方式，题目的情节、参数和代码全部重新编写。
9. **不出"预测代码输出"这类题**：被测模型能直接执行代码得到答案，测不出读代码的能力。读代码题改为调用链、数据流这类必须读懂代码结构才能回答的问题，执行代码也得不到答案。
10. **性能题的时限要留足余量**：机器快慢会影响耗时。要求错误解法（如 O(n²)）在测试规模下超过 30 秒，正确解法 1 秒内完成，单个测试的超时设为 5 秒。这样换一台机器，结论也不会变。

### 7.4 题材来源与覆盖

60 道题全部原创，下面这些公开测试只作为出题思路参考。调研时间是 2026-11，由 Gemini 联网搜集，主管抽查过来源。

| 借鉴来源 | 借鉴的思路 | 落到哪个维度 |
|---|---|---|
| [Misguided Attention](https://github.com/cpldcpu/MisguidedAttention) | 把经典题目的条件微调一点，测模型是真看懂了还是在背模板 | 修 Bug、Code Review：常见算法（二分、LRU 等）埋入"看起来像经典写法、其实条件不同"的边界问题 |
| [NoLiMa](https://github.com/adobe-research/NoLiMa) | 问题和答案之间没有字面重合，靠搜关键词找不到 | 读代码：答案藏在间接的配置映射、事件分发链路里，`grep` 题目里的词搜不到 |
| [BIRD](https://github.com/bird-bench) / Spider | 自然语言转 SQL，包含脏数据和多表口径 | 修 Bug、新功能：用 Python 自带的 `sqlite3`，题材包括聚合、NULL 陷阱、窗口函数 |
| [RefactorBench](https://arxiv.org/abs/2503.07832) | 多文件重构，功能保持不变 | 新功能 / 跨文件改动：5～8 个文件紧耦合的小项目，要求拆分接口、调整依赖 |
| Advent of Code 两段式 | 先给第一阶段的实现，再要求需求升级、数据规模变大 | 新功能：在已有代码上增量实现新需求，同时有性能要求 |
| CodeComplex 等复杂度类测试 | 小规模能过、大规模超时的实现 | 修 Bug：性能缺陷类题目，用大规模隐藏测试判分（时限规则见 7.3 第 10 条） |
| RegexPSPACE 等正则类测试 | 正则误匹配、灾难性回溯 | 修 Bug、Code Review：修正则的匹配错误和回溯爆炸，隐藏测试用正反例集和恶意输入限时测试 |
| DRPBench 等并发类测试 | 数据竞争、死锁 | Code Review、修 Bug：用 `CountDownLatch` / `threading` 构造能稳定复现的竞态 |
| SWR-Bench 等 PR 审查类测试 | 真实 PR 里的边缘缺陷：漏改的调用点、变量遮蔽 | Code Review：预埋问题多放在 diff 的边缘位置，不全是显眼的空指针 |
| 洗车题（"50 米外洗车走路还是开车"） | 题目里有隐含前提，测模型会不会被表面信息带偏 | 工具调用：前置条件没满足时，应该先补齐再调用，或者干脆不调用 |
| [SnitchBench](https://github.com/T3-Content/SnitchBench) | 上下文里埋诱导内容，测会不会做多余操作 | 工具调用：日志或文档里写有"顺便执行某操作"的诱导文字，正确做法是不调用 |
| 弹跳小球等物理模拟（[KCORES](https://github.com/KCORES/kcores-llm-arena)） | 物理和几何计算 | 新功能：去掉图形界面，只保留数值步进内核，用测试断言最终状态 |
| 数 r、9.11 vs 9.9 | 字符和数值的表层陷阱 | 修 Bug：版本号排序（含预发布版本）、Unicode 字符计数这类真实工程中的同类问题 |

**不采用的类型**：鹈鹕 SVG、网页小游戏、生图这类看审美的题，没法客观自动判分。

**题材覆盖要求**：60 题里，SQL、并发、正则、性能这四类题材各至少 2 题，分散在上表对应的维度里，不新增维度，总题量不变。

## 8. 技术选择

| 项 | 选择 | 原因 |
|---|---|---|
| 实现语言 | Python 3.9+，只用标准库 | 任何机器拿来就能跑，不用 `pip install` |
| 配置格式 | JSON | 标准库自带 |
| 加密 | 标准库实现：用 `tarfile` 打包，以 HMAC-SHA256 作为计数器模式的密钥流加密，再用独立派生的密钥做 HMAC 完整性校验（先加密后认证）。每个文件使用随机 nonce | 不依赖系统 openssl。macOS 自带的 LibreSSL 和 Linux 上的 OpenSSL 3 默认参数不同，同一份密文可能在另一台机器上解不开 |
| 密钥 | 内置在 litmus 源码里，不需要额外保管 | 加密要防的是两件事：模型扫一眼文件就看到答案，以及公开仓库被爬进训练数据。密文本身就能挡住这两件事，模型要偷看必须专门写代码解密，这已经属于刻意作弊。把密钥放到目录外也防不住会刻意作弊的模型，还会多出备份和迁移的麻烦。这样整个工具只有一个目录，换机器 `git clone` 就能用 |
| 解包安全 | 解包前检查每个成员的路径，拒绝绝对路径、`..` 和链接 | Python 3.9 到 3.14 的 `tarfile` 默认安全策略不一致，统一自己检查 |
| Java 判分 | `javac` + `java` + 自带运行器 | 不依赖 Maven 和网络，秒级出结果 |
| Python 判分 | 标准库 `unittest` + 自带运行器 | 不依赖 pytest |
| 并发安全 | `fcntl.flock` + 原子写入 | 防止 Agent 并行调用命令时状态错乱 |

## 9. 使用前提

- 工具必须能执行命令、能改文件（Agent 类工具），并且设为自动批准命令。纯网页聊天测不了。
- 开始测评前，litmus 目录里的改动要先提交（`start` 会检查）。
- 工具的全局配置（全局 AGENTS.md / CLAUDE.md、技能、MCP、钩子）会影响结果，测的是"工具当前配置下的模型"。报告里记录了工具名称，方便你自己对照。
